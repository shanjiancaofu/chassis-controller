# CMake and Ninja build

CubeMX remains the owner of `.ioc` files and generated peripheral code. Keep
`Toolchain / IDE` set to `STM32CubeIDE`; the repository CMake files are maintained
separately and are not generated by CubeMX.

Required tools:

- CMake 3.22 or newer.
- Ninja.
- GNU Arm Embedded 14.3.1 from STM32CubeIDE 14.3.rel1.
- Python 3 for OTA and factory packaging.

Put `arm-none-eabi-gcc`, `cmake`, and `ninja` on `PATH`. Alternatively, set
`ARM_GNU_TOOLCHAIN_ROOT` to the GNU Arm toolchain directory containing `bin/`.
The current CubeIDE 2.2.0 Windows installation uses the plugin's `tools/`
directory as this root; do not commit a machine-specific absolute path.

Configure and build all firmware targets:

```text
cmake --preset arm-release
cmake --build --preset arm-release
```

On Windows, when the tools are not on `PATH`, pass the tool locations without
putting machine-specific paths in the preset:

```text
cmake --preset arm-release \
  -DARM_GNU_TOOLCHAIN_ROOT=<gnu-arm-tools-directory> \
  -DCMAKE_MAKE_PROGRAM=<ninja-executable>
cmake --build --preset arm-release
```

Generated development artifacts are under `build/arm-release/`:

```text
application.elf / application.bin
bootloader.elf / bootloader.bin
qspi_factory_provisioner.elf / qspi_factory_provisioner.bin
```

The explicit source lists in `cmake/application.cmake`, `cmake/bootloader.cmake`,
and `cmake/provisioner.cmake` define target ownership. When CubeMX generates a
new peripheral source or a hand-written module is added, add it only to the
target that owns it. Do not use recursive source globbing.

The CMake build is the primary command-line build. Keep CubeIDE available for
debugging and output comparison until the workflow has accumulated sufficient
target-board use. CubeMX continues to generate peripheral code from each `.ioc`;
after generation, review the diff and update the owning target's explicit source
list if CubeMX added or removed a source file.
