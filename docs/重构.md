# Application 原生平台化重构

本文维护 STM32G474 Application 的目标架构、固定边界、迁移批次和验收规则。后续可以在对应
章节补充已经确认的接口、工具能力和验证要求；与当前代码不一致的旧方案应直接修订或删除，
不在本文并列保留多套互相冲突的路线。

## 总体原则

> **参考 Zephyr 已经验证成熟的架构设计，好的设计直接采用，不为了“显得是自己的”而改名、改语义、重新发明一套。**
>
> **但不克隆 Zephyr 仓库，不引入 `third_party/zephyr`，不复制它的 Python/CMake 工具，不依赖 west。Kconfig/Devicetree 生成、linker 集成、构建检查这些工具由 `chassis-controller` 自己实现。**
>
> **保留 STM32 HAL + CMSIS + FreeRTOS，并长期保留 CubeMX 与 `.ioc` 作为底层外设初始化的权威配置源。换的是固件基础架构，不重写已经验证的产品逻辑。**

核心边界是：**不把 Zephyr 当依赖，只把它当架构参考实现。**

当前基线已经做过一轮边界整理，但 `application.cmake` 仍把 CubeMX、HAL、FreeRTOS、app、BSP、UI、通信、组件、模块全部堆在一个大列表里；`board_config.h` 仍然通过宏把 `hfdcan2/hspi3/htim8/...` 暴露给 BSP；`ChassisApp_Init()` 仍手工启动大量设备。

这轮就把这三个根问题彻底解决。

# 1. 最终技术路线先定死

最终不是：

```text
FreeRTOS 项目
+
模仿了一些 Zephyr 命名
```

而是：

```text
                  chassis application
                         │
                 modules / subsys / ui
                         │
                  Zephyr式 driver API
                         │
                    struct device
                         │
                config / data / api
                         │
              STM32 concrete drivers
                         │
                 STM32 HAL / CMSIS
```

横向还有：

```text
Kconfig
   │
   └── CONFIG_*

Devicetree
   │
   └── DT_* / device instance

SYS_INIT
   │
   └── linker sections

FreeRTOS
   │
   └── scheduler / task / queue
```

这几个以后不再换。

Zephyr 当前仍然是静态 device + init entries + linker section 这一套，而不是运行时注册设备；其 `kernel/init.c` 也是遍历静态 init/device entries。([github.com][1])

# 2. 哪些 Zephyr 设计直接采用

这部分不要自己再设计另一套名字。

| Zephyr 成熟设计                                      | chassis-controller |

| `DEVICE_DEFINE()`                                | 采用                 |
| `DEVICE_DT_DEFINE()`                             | 采用                 |
| `DEVICE_DT_GET()`                                | 采用                 |
| `config / data / api`                            | 原样采用               |
| `SYS_INIT()`                                     | 采用                 |
| `EARLY`                                          | 采用                 |
| `PRE_KERNEL_1`                                   | 采用                 |
| `PRE_KERNEL_2`                                   | 采用                 |
| `POST_KERNEL`                                    | 采用                 |
| `APPLICATION`                                    | 采用                 |
| linker iterable section                          | 采用                 |
| Devicetree node/status/chosen/aliases/compatible | 采用                 |
| Kconfig `CONFIG_*`                               | 采用                 |
| driver `int + -errno`                            | 采用                 |
| `struct can_frame` 思路                            | 采用                 |
| `sensor_value` 思路                                | 可以采用               |
| `gpio_dt_spec` 思路                                | 采用                 |

例如 Zephyr 当前 sensor API 已经带上 RTIO 等较深的 Zephyr 运行时依赖，所以 ICM45686 不能整套搬。我们参考它的设备组织、通道、配置、寄存器处理，但不用 RTIO。([GitHub][2])

# 6. `struct device` 自己实现，但设计不要乱改

我们自己的：

```text
include/device.h
kernel/device.c
```

不复制 Zephyr 源文件。

但是接口保持这个模型：

```c
struct device_state {
    int init_res;
    bool initialized;
};

struct device {
    const char *name;

    const void *config;
    void *data;
    const void *api;

    struct device_state *state;
};
```

初始化：

```c
typedef int (*device_init_t)(const struct device *dev);
```

状态：

```c
bool device_is_ready(const struct device *dev);
```

初始化规则：

```text
init_fn() == 0
    initialized = true
    init_res = 0

init_fn() < 0
    initialized = true
    init_res = errno
```

所有 driver：

```text
0
-EINVAL
-ENODEV
-EIO
-ETIMEDOUT
-EBUSY
-ENOSPC
-ENOTSUP
```

不要再：

```c
bool Start()
```

然后上层只能知道：

```text
false
```

Zephyr 的 driver API 本身也大量使用 device pointer + errno 返回，这是值得直接采用的部分，例如 UART driver API 就是这种模式。([GitHub][3])

# 8. `DEVICE_DEFINE()` 自己实现

例如我们自己的宏：

```c
#define DEVICE_DEFINE(dev_id, dev_name, init_fn, data_ptr, cfg_ptr, \
                      level, prio, api_ptr)                        \
    static struct device_state dev_id##_state;                    \
                                                                    \
    const struct device dev_id                                    \
        __attribute__((section(".device")))                        \
        __attribute__((used)) = {                                  \
            .name = dev_name,                                      \
            .config = cfg_ptr,                                     \
            .data = data_ptr,                                      \
            .api = api_ptr,                                        \
            .state = &dev_id##_state,                              \
        };                                                          \
                                                                    \
    INIT_ENTRY_DEFINE(dev_id, init_fn, &dev_id, level, prio)
```

注意：

这是我们的实现。

不是复制 Zephyr `device.h`。

但是：

```text
DEVICE_DEFINE
device config/data/api
init entry
```

这套设计不重新发明。

# 10. Linker section 自己实现

当前 application linker 保持：

```text
FLASH:
0x08008000
480 KiB

RAM:
0x20000000
128 KiB
```

在现有 linker script 加：

```ld
__init_EARLY_start = .;
KEEP(*(SORT_BY_NAME(.z_init_EARLY_P_?_SUB_*)))
KEEP(*(SORT_BY_NAME(.z_init_EARLY_P_??_SUB_*)))
KEEP(*(SORT_BY_NAME(.z_init_EARLY_P_???_SUB_*)))

__init_PRE_KERNEL_1_start = .;
...

__init_PRE_KERNEL_2_start = .;
...

__init_POST_KERNEL_start = .;
...

__init_APPLICATION_start = .;
...

__init_end = .;
```

以及：

```ld
__device_start = .;
KEEP(*(SORT_BY_NAME(.device*)))
__device_end = .;
```

为什么 `? / ?? / ???`：

因为：

```text
1
2
10
50
100
```

必须保持数字优先级。

不能简单字符串排序。

Zephyr 的 linker/init architecture 也是依赖静态 linker section 来解决这个问题，而不是手写 InitAll。([GitHub][1])

# 11. `kernel/init.c` 很简单

我们自己写：

```c
static int InitEntry_Run(const struct init_entry *entry)
{
    int ret;

    ret = entry->init_fn(entry->dev);

    if (entry->dev != NULL) {
        entry->dev->state->initialized = true;
        entry->dev->state->init_res = ret;
    }

    return ret;
}
```

然后：

```c
int SystemInit_RunLevel(enum init_level level);
```

负责：

```text
[start, end)
```

逐个调用。

不要额外搞：

```text
InitManager
DependencyGraph
DeviceRegistry
StartupService
```

这些全部多余。

# 23. CAN 公共 API 按成熟设计来

当前：

```c
typedef struct {
    uint32_t identifier;
    uint8_t length;
    uint8_t data[64];
} BspFdcanFrame;
```

改：

```c
struct can_frame {
    uint32_t id;
    uint8_t dlc;
    uint8_t flags;
    uint8_t data[64];
};
```

API：

```c
struct can_driver_api {
    int (*start)(const struct device *dev);
    int (*stop)(const struct device *dev);

    int (*send)(const struct device *dev,
                const struct can_frame *frame);

    int (*recv)(const struct device *dev,
                struct can_frame *frame);

    int (*recover)(const struct device *dev);

    int (*get_state)(
        const struct device *dev,
        enum can_state *state,
        struct can_bus_err_cnt *err_cnt);
};
```

公共 wrapper：

```c
int can_start(const struct device *dev);
int can_send(const struct device *dev,
             const struct can_frame *frame);
```

Zephyr CAN API 本身就是 device + common CAN frame/filter/controller abstraction，这个总体设计不需要我们重新发明。([GitHub][4])
