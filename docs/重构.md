> 基线：`shanjiancaofu/chassis-controller` `develop` 分支
> 核对提交：`50bd322e7342b84135ea10791c61889d65d7bcd2`
> 核对时间：2026-08-20

---

## 0. 结论先写清楚

原方案的核心方向是对的：

> **不把 Zephyr 作为 RTOS 或源码依赖，而是采用它已经验证成熟的 Device Model、driver API、静态初始化、Devicetree、Kconfig 和构建分层思想；底层继续使用 STM32 HAL + CMSIS + FreeRTOS + CubeMX。**

但原文需要做几处实质修正，否则会出现“名字像 Zephyr，语义却不一致”的问题。

这版固定以下原则：

1. **保留当前已经落地且正确的 Device Model / linker init section，不倒退重写。**
2. **`struct device` 以 Zephyr 当前实现为参考，保留 `config / data / api / state / ops`。**
3. **Devicetree 必须描述真实设备拓扑，而不是扁平的设备清单。**
4. **DTS 不保存 `hfdcan2`、`hspi3` 这类 CubeMX C 符号字符串。**
5. **`.ioc` 继续是 STM32 寄存器级初始化的权威来源；DTS 不重复抢占同一份硬件配置的所有权。**
6. **Kconfig 语言继续使用，但不再把“自己重新实现完整 Kconfig 解释器”作为目标。**
7. **标准 DTS 语法交给 `dtc`；项目只维护自己的 DTB 后处理、绑定校验和 C 宏生成。**
8. **驱动初始化失败与产品是否允许启动分开：driver 只报告错误，required/optional 由产品层决定。**
9. **FreeRTOS 只允许出现在 RTOS runtime 和少数明确的并发实现内部，不继续横向污染 app/modules/subsys。**
10. **现有 OTA、CAN ISR、PID、Safety、Command、Odometry、IMU fusion、LCD UI 等成熟业务逻辑不重写。**

最终目标不是“做一个迷你 Zephyr”，而是：

```text
CubeMX/.ioc + STM32 HAL
        │
        ▼
STM32 concrete drivers
        │
        ▼
generic driver API
        │
        ▼
static struct device
        │
        ├── Devicetree：设备拓扑 / 角色 / 静态属性
        ├── Kconfig：软件功能 / 队列 / 栈 / 周期 / 编译选项
        └── static init：初始化顺序
        │
        ▼
communication / subsys / modules / ui
        │
        ▼
chassis application
        │
        ▼
FreeRTOS task runtime
```

# 2. 原文第一个需要修正的地方：Device Model

## 2.1 继续沿用当前 `struct device`

最终建议：

```c
struct device_state {
    int init_res;
    bool initialized;
};

struct device_ops {
    int (*init)(const struct device *dev);
};

struct device {
    const char *name;

    const void *config;
    const void *api;

    struct device_state *state;
    void *data;

    struct device_ops ops;
};
```

暂时不要为了追 Zephyr 每一个新特性加入：

```text
device dependency handle
device PM
deinit
userspace
syscall
device metadata
dynamic device dependencies
```

这些当前项目都不需要。

原则：

```text
跟 Zephyr 保持同一种 Device Model 思路
≠
复制 Zephyr struct device 的所有字段
```

---

## 2.2 `config / data / api / ops` 的职责固定

```text
config
    编译期/板级固定配置
    HAL handle
    pin/channel mapping
    immutable hardware properties

data
    运行时状态
    queue
    counters
    error state
    DMA state

api
    对外 driver function table

ops
    device 生命周期操作
    当前只需要 init
```

例如：

```c
struct can_stm32_fdcan_config {
    FDCAN_HandleTypeDef *handle;
    uint8_t filter_capacity;
};

struct can_stm32_fdcan_data {
    struct can_frame rx_queue[CONFIG_CAN_RX_QUEUE_SIZE];

    volatile uint8_t rx_head;
    volatile uint8_t rx_tail;
    volatile uint8_t rx_count;

    uint32_t error_events;
    struct can_bus_err_cnt error_counters;
};
```

HAL handle 可以存在于：

```text
boards/
drivers/*stm32*
Core/
```

但不能进入：

```text
app/
modules/
communication/
subsys/
ui/
```

# 3. 原文第二个需要修正的地方：`SYS_INIT()` 和 device init 失败语义

这里原文有一个逻辑冲突。

一方面原文说：

```text
required device 失败 → fail-fast
optional device 失败 → degraded
```

另一方面又让：

```c
SystemInit_RunLevel(...)
```

遇到任何 device init 负值就直接返回。

这样 optional device 一旦失败，系统也会停止。

两者不能同时成立。

---

## 3.1 Zephyr 本身怎么做

Zephyr 的 `SYS_INIT()` 返回值并不用来决定 boot 是否终止。

device 初始化结果则保存在 device state，之后：

```c
device_is_ready(dev)
```

反映设备是否初始化成功。

这套“初始化结果”和“产品启动策略”分离的思想应该采用。

---

## 3.2 chassis-controller 最终规则

### init runner 负责：

```text
按 level + priority 执行
记录每个 device init 结果
继续完成本 level 的其余初始化
```

### 产品策略负责：

```text
required device：
    CAN
    motor
    encoder
    safety-critical GPIO
    power path（按实际需要）

optional device：
    IMU
    LCD
    SR501
    某些 telemetry device
```

例如：

```c
static bool PlatformRequiredDevicesReady(void)
{
    return device_is_ready(DEVICE_DT_GET(DT_CHOSEN(chassis_can))) &&
           device_is_ready(DEVICE_DT_GET(DT_CHOSEN(chassis_drive))) &&
           device_is_ready(DEVICE_DT_GET(DT_CHOSEN(chassis_left_encoder))) &&
           device_is_ready(DEVICE_DT_GET(DT_CHOSEN(chassis_right_encoder)));
}
```

optional：

```c
if (!device_is_ready(imu_dev)) {
    SystemStatus_SetDegraded(SYSTEM_DEGRADED_IMU);
}
```

不要让 CAN driver 自己决定：

```text
CAN 初始化失败后整个产品是否应该死机
```

driver 只返回：

```text
-ENODEV
-EIO
-ETIMEDOUT
...
```

---

# 4. 原文第三个需要修正的地方：初始化 level 的语义不能假装与 Zephyr 完全相同

Zephyr 当前定义：

```text
EARLY
    非常早

PRE_KERNEL_1
PRE_KERNEL_2
    kernel service 不可用

POST_KERNEL
    kernel 已经 alive，可以使用 kernel primitive

APPLICATION
    application main 前
```

但你这里是：

```text
STM32 HAL + CMSIS-RTOS2 + FreeRTOS
```

不是 Zephyr kernel。

所以名字可以采用，但语义必须明确写成“映射”。

---

## 4.1 chassis-controller 的最终映射

建议：

```text
HAL_Init
SystemClock_Config

EARLY
    只允许最早期 platform/safety 初始化
    不依赖 CubeMX peripheral handle 已完成初始化

MX_GPIO_Init
MX_DMA_Init
MX_ADC...
MX_FDCAN...
MX_SPI...
MX_TIM...
MX_IWDG...

PRE_KERNEL_1
    HAL peripheral 已创建
    FreeRTOS kernel 尚未 initialize

PRE_KERNEL_2
    concrete device driver 初始化
    仍禁止阻塞式 RTOS 操作

PlatformRequiredDevicesReady()

osKernelInitialize()

POST_KERNEL
    CMSIS-RTOS2 kernel 已 initialize
    可以创建 RTOS object
    但 scheduler 尚未运行
    禁止依赖任务调度的阻塞流程

MX_FREERTOS_Init()

APPLICATION
    product composition
    ChassisApp_Init()
    启动前状态检查
    仍不允许电机自动产生非零输出

osKernelStart()
```

注意：

> **POST_KERNEL 在本项目里不是“完全等价 Zephyr POST_KERNEL”。**

在 scheduler 尚未启动前：

```text
delay
等待另一个 task
依赖 task 被调度的 semaphore handshake
```

都不能放这里。

---

## 4.2 当前 `main.c` 还没到这个状态

当前只运行了：

```text
EARLY
PRE_KERNEL_1
PRE_KERNEL_2
```

而：

```text
ChassisApp_Init()
```

仍发生在：

```text
osKernelInitialize()
```

之前。

`POST_KERNEL` 和 `APPLICATION` 目前没有真正接入 boot flow。

因此新版把这一项列为待完成，不再写成“已经最终完成”。

# 5. Devicetree：必须从“设备清单”升级为“硬件拓扑”

这是当前最重要的剩余架构问题之一。

## 5.1 当前 DTS 的优点

现在已经有：

```text
chosen
aliases
compatible
status
bindings
phandle
```

方向正确。

---

## 5.2 DTS 扁平清单问题已解决

旧版曾经是：

```dts
can0: can { ... };
imu0: sensor { ... };
display0: display { ... };
flash0: flash { ... };
drive0: motor-controller { ... };
```

所有设备平铺在 `/` 下，并带 C handle/bus 字符串。当前 DTS 已移除这些属性，SPI2/LCD、
SPI3/IMU、QSPI/Flash、ADC1/电源采样已经使用 controller/child 和 `reg`；GPIO consumer 使用
`gpios` phandle-array，phandle 由 `dtc -@` 生成。

以下旧属性已不存在：

```dts
cubemx-handle = "hfdcan2";
cubemx-handle = "hspi3";
cubemx-handle = "htim8";
```

以及：

```dts
bus = "spi3";
```

这种字符串。

这不是应该长期保留的 DeviceTree 关系。

---

## 5.3 HAL C symbol 不进入 DTS

必须删除：

```text
cubemx-handle = "hfdcan2"
cubemx-handle = "hspi3"
cubemx-handle = "htim8"
```

DTS 是硬件描述，不应该知道：

```text
STM32CubeMX 最终生成的 C 变量名是什么
```

HAL handle 绑定在 C 层完成：

```c
#define CAN_NODE DT_NODELABEL(fdcan2)

static const struct can_stm32_fdcan_config can_config = {
    .handle = &hfdcan2,
    .filter_capacity = DT_PROP(CAN_NODE, standard_filter_count),
};
```

这样：

```text
DTS
    知道 fdcan2 是哪个硬件节点

board/driver C
    知道 fdcan2 对应 &hfdcan2
```

两层职责分开。

# 6. `.ioc` 和 DTS 的 source-of-truth 重新定义

原文虽然意识到了双源问题，但还重复存了太多硬件参数。

例如同时让：

```text
.ioc
```

和：

```dts
bitrate = <500000>;
sample-point = <800>;
bitrate-data = <2000000>;
sample-point-data = <824>;
```

共同保存 FDCAN bit timing。

如果 `.ioc` 被定义为寄存器初始化权威源，这种重复不应该长期存在。

---

## 6.1 最终职责

### CubeMX `.ioc`

权威负责：

```text
MCU 型号
clock tree
pin mux
GPIO mode
DMA
NVIC
peripheral instance
FDCAN timing register
SPI controller prescaler/mode
TIM prescaler/period/channel
ADC configuration
IWDG configuration
RTC clock/source
HAL handle 的生成
```

### DTS

负责：

```text
设备存在性
设备拓扑
controller ↔ child device 关系
chosen
aliases
compatible
status
chip 静态属性
GPIO role
SPI peripheral 的 max-frequency
flash capacity / erase size
逻辑设备之间的 phandle 关系
```

### Kconfig

负责：

```text
软件是否编译
queue depth
task stack
task priority
period
timeout
debug feature
test feature
algorithm option
```

一句话：

```text
.ioc = STM32 寄存器配置
DTS  = 硬件拓扑和设备关系
Kconfig = 软件功能
```

---

## 6.2 不再为了“像 Zephyr”把同一参数复制两份

如果参数已经完全由 CubeMX 初始化，例如：

```text
TIM8 ARR
FDCAN nominal timing
FDCAN data timing
SPI peripheral prescaler
```

默认不要再手工写一份 DTS 值。

如果某个值必须同时暴露给软件：

```text
由工具从 .ioc 生成 manifest
```

或者：

```text
DTS 只保存软件真正要消费的语义值
```

而不是要求开发者手工同步两份。

`verify_hw_config.py` 继续存在，但目标是验证：

```text
fdcan2 是否真的存在
spi3 是否真的是 IMU bus
tim8 是否真的是 drive timer
tim2/tim4 是否真的是 encoder timer
```

而不是制造更多双源。

# 7. 推荐的 DTS 结构

最终应有一个 SoC/MCU 层的逻辑拓扑文件，例如：

```text
dts/stm32/stm32g474.dtsi
```

里面提供稳定 node label：

```dts
/ {
    soc {
        fdcan2: can-controller@2 {
            compatible = "st,stm32g4-fdcan";
            status = "disabled";
        };

        spi2: spi-controller@2 {
            compatible = "st,stm32g4-spi";
            status = "disabled";
        };

        spi3: spi-controller@3 {
            compatible = "st,stm32g4-spi";
            status = "disabled";
        };

        tim8: timer@8 {
            compatible = "st,stm32g4-timer";
            status = "disabled";
        };
    };
};
```

这里的 `@2/@3/@8` 只是本项目的逻辑 unit-address 方案时可以使用；如果以后维护准确 peripheral base address，则改为真实地址。

board DTS：

```dts
/dts-v1/;

/include/ "../../dts/stm32/stm32g474.dtsi"

/ {
    model = "Chassis Controller STM32G474VET6";
    compatible = "shanjiancaofu,chassis-g474";

    chosen {
        chassis,can = &fdcan2;
        chassis,imu = &imu0;
        chassis,display = &display0;
        chassis,flash = &flash0;
        chassis,drive = &drive0;
    };
};

&fdcan2 {
    status = "okay";
    standard-filter-count = <2>;
};

&spi3 {
    status = "okay";

    imu0: imu@0 {
        compatible = "invensense,icm45686";
        reg = <0>;
        spi-max-frequency = <1328125>;
        status = "okay";
    };
};

&spi2 {
    status = "okay";

    display0: display@0 {
        compatible = "sitronix,st7789v";
        reg = <0>;
        width = <320>;
        height = <240>;
        status = "okay";
    };
};
```

重点不是照抄这一段，而是关系必须变成：

```text
SPI3 controller
    └── ICM45686

SPI2 controller
    └── ST7789V
```

而不是：

```text
imu0
    bus = "spi3"
```

# 9. `devicetree_generated.h` 必须变成内部实现，不允许上层直接依赖生成命名

当前生成器会生成：

```text
DT_NODE_CAN0
DT_PROP_CAN0_BITRATE
DT_CHOSEN_CHASSIS_CAN
DT_NODELABEL_...
```

下一步增加稳定公共头：

```text
include/devicetree.h
```

上层只使用：

```c
DT_NODELABEL(fdcan2)
DT_ALIAS(can)
DT_CHOSEN(chassis_can)

DT_NODE_HAS_STATUS(node, okay)
DT_PROP(node, prop)
DT_PROP_OR(node, prop, default_value)

DEVICE_DT_GET(node)
```

不要让业务代码写：

```c
DT_PROP_CAN0_STANDARD_FILTER_COUNT
```

原因：

```text
这是 generator internal macro
```

generator 一旦换编码策略，上层就会全部被绑死。

# 10. `DEVICE_DT_DEFINE()` 必须真正由 DT node 驱动

当前：

```c
DEVICE_DT_DEFINE(can0, ...)
```

本质上仍等价于：

```c
DEVICE_DEFINE(can0, "can0", ...)
```

`can0` 只是一个 C token。

最终要做到：

```text
DTS node-id
    ↓
device symbol
    ↓
device instance
```

例如公共语义：

```c
#define CAN_NODE DT_NODELABEL(fdcan2)

DEVICE_DT_DEFINE(
    CAN_NODE,
    CanStm32Fdcan_Init,
    &can_data,
    &can_config,
    PRE_KERNEL_2,
    50,
    &can_stm32_fdcan_api);
```

同时生成器必须提供：

```text
node exists
status okay
node-id → device symbol
chosen → node-id
alias → node-id
```

并支持：

```c
DEVICE_DT_GET(DT_CHOSEN(chassis_can))
```

而不是让：

```text
DEVICE_DT_GET
```

只是给 `DEVICE_GET()` 换一个名字。

# 11. device 实例化必须 status-aware

最终：

```dts
status = "disabled";
```

的节点不能继续产生可用 device instance。

需要支持至少：

```c
DT_NODE_HAS_STATUS(node_id, okay)
```

以及：

```text
只有 status = okay 的节点参与 DEVICE_DT_DEFINE
```

如果一个 driver 支持多实例，后续再增加：

```text
DT_INST
DEVICE_DT_INST_DEFINE
```

第一阶段不必强行实现完整 Zephyr instance macro 系统。

但必须先把：

```text
DT node
→ device object
```

这条链做真。

# 16. Driver API：沿用 Zephyr 风格，但不机械复制 Zephyr 整个 API

## 16.1 CAN

当前：

```c
struct can_frame {
    uint32_t id;
    uint8_t dlc;
    uint8_t flags;
    uint8_t data[64];
};
```

是正确方向。

建议补齐基本 flags：

```text
IDE
RTR
FDF
BRS
ESI（如果驱动能够提供）
```

当前 filter：

```c
struct can_filter {
    uint32_t id;
    uint32_t mask;
};
```

建议增加：

```c
uint8_t flags;
```

否则无法干净地区分：

```text
standard 11-bit
extended 29-bit
```

Zephyr 当前 `can_filter` 也有 `flags`。

---

## 16.2 CAN generic API 不要放 STM32 FDCAN 私有能力

generic：

```text
start
stop
send
recv
recover
state/error counters
filter
```

STM32-specific：

```text
TX event marker
message RAM 特殊诊断
restricted-mode raw state
FDCAN peripheral-specific debug data
```

放：

```text
drivers/can/can_stm32_fdcan_ext.h
```

或 concrete driver 内部。

不要继续扩张：

```c
struct can_driver_api
```

直到它只适用于 STM32。

---

## 16.3 Sensor

ICM45686 driver：

```text
SPI transfer
WHO_AM_I
ODR
FSR
FIFO
interrupt
DMA
raw → SI
```

模块层：

```text
Mahony
姿态
yaw/pitch/roll
状态估计
```

继续分开。

当前：

```text
components/icm45686
drivers/sensor/icm45686_stm32.c
modules/sensors/imu_orientation.c
components/imu_fusion
```

大方向已经正确，不要为了目录名字再推翻。

---

## 16.4 GPIO

最终应该形成：

```c
struct gpio_dt_spec {
    const struct device *port;
    uint16_t pin;
    uint16_t flags;
};
```

产品语义：

```text
Emergency Stop
Button
LED
SR501
```

不要都继续做成独立 STM32 HAL 封装层。

例如：

```text
GPIO pin
   ↓
generic GPIO API
   ↓
SafetyManager
```

而不是：

```text
EmergencyStop STM32 driver
   ↓
SafetyManager
```

E-stop 的：

```text
latch
clear policy
motion inhibit
fault semantics
```

属于 safety module。

        DEVICE_DT_GET(DT_CHOSEN(chassis_can));

# 21. 安全启动顺序继续高于“自动 device init”

底盘项目最重要的不是架构漂亮，而是：

```text
上电绝不能意外输出非零 PWM
```

固定：

```text
reset
  ↓
GPIO safe state
  ↓
PWM compare = 0
  ↓
HAL peripheral init
  ↓
device initialization
  ↓
required-device validation
  ↓
SafetyManager
  ↓
parameters
  ↓
control modules
  ↓
communication
  ↓
RTOS objects/tasks
  ↓
scheduler
  ↓
显式 StartControl()
```

任何 device 被 `DEVICE_DT_DEFINE()` 并自动初始化：

```text
≠ motor enabled
≠ control active
≠ PWM non-zero
```

motor driver 的 init 最多做到：

```text
hardware ready
output safe
```

不能做到：

```text
开始运动
```

# 22. Watchdog 顺序单独处理

IWDG 一旦启动不能像普通 peripheral 一样假设可以关掉。

因此 watchdog device 不能为了统一流程被随意搬动。

建议：

```text
CubeMX IWDG creation
    保持已验证行为

watchdog driver
    负责 refresh / state / policy-facing API

AppWatchdog_ConfigureNormal()
    逐步迁成 watchdog driver / watchdog subsystem 的明确启动策略
```

迁移时必须回归：

```text
bootloader → application
debug freeze
normal feed
task health timeout
fault reset
OTA
```

不要因为 Device Model 重构改变已验证的 watchdog 时序。
